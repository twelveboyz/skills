# Skill 执行效率审计

审一个 skill 从用户开口到拿到结果这条链路上的**空转**：不产生新信息、不推进状态的调用、等待和重跑。

只审**调用结构**。业务规则冲突记录不裁决；代码风格与业务正确性不在范围内；skill 的质量评分归 `darwin-skill`，这里只算它跑一趟花多少轮。

## 输入

| 输入 | 内容 | 缺失时 |
|---|---|---|
| `TARGET` | 目标 skill 目录，或 skill 标识列表（可一次审多个） | 问，一次问全 |
| `TASK` | 一次典型任务的自然语言描述：用户怎么开口、期望拿到什么 | 问，一次问全 |
| `MODE` | `diagnose` 已经慢了找原因 / `prevent` 未上线提前审 / `regress` 改造后回归 | 按有无 `TRACE` 推断并说明推断 |
| `TRACE` | 已有会话归档、执行日志、耗时记录路径 | 自己采集 |

开工前回一句：用哪几条命令、哪几个用例建基线，预计拿到哪六项指标（见 [METRICS.md](METRICS.md)）。

## 循环

六步，顺序固定。文档、注释、README、示例命令一律当待验证项：`--help` 与代码常量才是参数的唯一事实源，逐条与实现核对。

1. **结构盘点** — 列 `TARGET` 下全部文件与行数，标出每次执行都会被读的（主文档、被引用的子文档、`--help` 输出）。
   完成条件：N_read 的理论下限是一个具体数字。

2. **调用链还原** — 把 `TASK` 拆成原子步骤填下表。无 `TRACE` 就照文档自己跑一遍，边跑边记。**这张表就是基线**，后续所有对比以它为准。

   | # | 步骤 | 需工具调用 | 需等用户 | 失败需从头重跑 | 输出体量 | 备注 |
   |---|---|---|---|---|---|---|

   完成条件：每行的「需工具调用」都是具体数字，全表加得出 N_call。

3. **慢因扫描** — 按 [FAILURE-MODES.md](FAILURE-MODES.md) 的 A–G 七类逐项过，每项给出「信号 → 证据（文件:行号 或 步骤号）→ 根因 → 修复」四件套。
   完成条件：写进报告的每条都带 `file:line` 或步骤号；写不出证据的那条不进报告。

4. **归因与排序** — 每个问题算影响分 `额外调用数 × 出现频率`，降序排。
   完成条件：只对前 3 项出详细改造方案，其余列一行清单。

5. **改造** — 从 [REPAIR-MOVES.md](REPAIR-MOVES.md) 选手法，每个写清：改哪个入口/函数、加哪个参数、删哪段文档。
   完成条件：动源码前确认版本控制状态（不受控先备份带时间戳的副本），改完立即做语法/可加载性检查。

6. **验证** — 跑 [VERIFICATION.md](VERIFICATION.md) 的四个用例，逐个写命令、期望指标、实测指标、结论。
   完成条件：四行都有实测数字，正常路径的产出逐条 diff 为 IDENTICAL。

## 产出

四段，顺序不变。

1. **基线表** — 第 2 步那张表 + 六项指标现状，并声明本次的目标值。
2. **问题清单**（影响降序）— 编号 / 类别 A–G / 现象一句话 / 证据 / 根因（机制层，不是「没写好」）/ 修复动作 / 预期指标改善。
3. **改造方案** — 改造后的文档骨架（一条黄金命令 + 参数真值表 + 三类失败的处理方式）、黄金命令本身、参数真值表、文件级改动清单。
4. **验证计划** — 四用例表 + 每个用例的实测结果。

## 边界

外部接口报的数字与项目规则给的数字冲突时，问用户要哪个，不把接口的物理上限当业务规则。

单个样本上观察到的现象标注为样本，推广到同类对象前先扩大样本。
