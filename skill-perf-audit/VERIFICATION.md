# 验证（不可跳过）

四个用例。每个写：**命令、期望指标、实测指标、结论**。四行都有实测数字才算通过。

| 用例 | 目的 | 通过标准 |
|---|---|---|
| 正常路径 | 改造没改变产出 | 逐条 diff 为 IDENTICAL（不是只比条数） |
| 典型失败路径 | 恢复粒度正确 | 只重发失败单元，已完成单元不重复执行 |
| 歧义输入 | 提前失败 | 解析阶段报错并打印映射表，不进入执行 |
| 缺资源场景 | 不静默降级 | 显式失败并指明期望位置，或降级有醒目标记 |

## 逐条 diff 的做法

- 改造前后各跑一次**同一份输入**，产物逐行比对，输出 `added / removed` 计数与差异样本。
- 条数相等不等于内容正确：条数相同但字段错位是常见结果，比「有变化」更难发现。
- 改造前先留可回退的副本，产物落盘到独立目录，不覆盖原始产物。

## 构造失败路径

- 用一个必然失败的最小单元（不存在的 ID、越界的批次），确认重试只覆盖该单元。
- 检查已完成单元的副作用次数：重复执行会体现在接口侧的调用记录或产物时间戳上。

## 构造缺资源场景

- 屏蔽首选资源要用「只含单个 stub 的空目录」加绝对路径调用，不改 `PATH` 的其余部分——覆盖整个 `PATH` 会连带屏蔽命令自身的依赖工具，制造假失败。
- 断言看日志里的醒目标记，不只看退出码：退出码 0 正是静默降级的伪装。
